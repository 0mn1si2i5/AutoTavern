## 比赛能够证明什么

唯一一场 practice `df34218fbf134a31975081faae0ae3c9`：15 回合、第 2/8 名，
一名 Agent 加七个服务器规则机器人。482 个决策对应 482 个服务器 `committed` 确认。
这证明了该场的鉴权、执行、完整结束路径，不能估计其他 Agent 对抗强度或真实游戏胜率。
原始目录 `runs/practice-20261028-103720/` 与压缩包未修改。

本次重新加载冻结权重，482 个动作及理由全部重放一致。这里只重放策略输入输出，
没有服务器种子和战斗随机状态，不能重建原对局，也不能声称修改后的模型能在这局吃鸡。

| 观察 | 已确认的事实 | 尚不能据此断言 |
| --- | --- | --- |
| 无效站位循环 | 482 个决策中 279 次移位；159 次移位返回本段已出现的可见排列 | 每次移位都无价值，或循环造成了某个具体名次损失 |
| 操作上限 | 第 8 回合 87 次移位，第 9 回合 79 次；两回合均在第 100 次操作后进入下一回合 | 这两回合因此漏花金币：最后一次操作前金币已经为 0 |
| 手牌转化 | 第 8–13 回合末持续持有精英导航员、红色多彩幼龙等牌；其中一些跨多回合未打出 | 所有保留都错误：满场时需要比较替换、战吼收益和当前战力 |
| 经济节奏 | 第 8 回合末仍为二本，第 14 回合才升六本 | 必须按固定回合升本；英雄、商店与即时血量会改变取舍 |
| 终局空位 | 第 14、15 回合点击结束时确实只有六个随从、空手、0 金币，不是从战后截图推断 | 无条件凑满七个一定更强；第 15 回合进行了投球手等买卖与增益转化 |

277 次有同回合后续观测的移位，均与引擎 `remove(from); insert(to)` 的排列预测相符。
其余两次就是打满额度后的跨回合边界，没有冒充已验证的同回合后继。

## 本地修复

`omnibob/reorder_exit.py` 实现 `ReorderExitPolicy`：在连续移位段中记住可见的己方排列，
模型下一次首选移位若返回旧排列，则临时屏蔽移位，再由同一网络选择其他合法动作。
不强制结束、不设每回合固定移位数；实际非移位动作、回合改变或棋盘内容改变后重新开始记录。
不同身材、附加物的同名随从被区分。对手公开信息变化不清空本方站位历史。

该模块只接收 `ObservationV2`，没有游戏句柄、存档或随机流。它放在原 RepeatGuard 内层，
使 RepeatGuard 只记录最后真正返回的动作，避免为被丢弃的提案增加计数。
模型、旧 RepeatGuard、旧 MoveGuard、原生引擎与默认加载器均未修改。
新增控制器可能选择更早卖出/结束，也可能阻止有用的返回站位，因此必须看完整对局结果。

另外修复了结构化请求日志丢失终局嵌套 `match` 元数据的问题，保留比赛 ID、状态、席位、
名次和模型标识，仍不收集任意响应字段或鉴权信息。该修复通过离线协议形状测试，未重新上线验证。
冻结包内的旧独立审计器仍按旧响应格式工作；原 practice 的 `audit-live.json` 和适配脚本保留，
没有改写旧审计失败记录，也没有把这个日志修复称为完整审计器迁移。

## 对照设计

权重始终为 `runs/releases/omnibob-v0.2-20261028/policy/policy.pt`，SHA256：
`3e0efb0636a2d7abd2b51c1dfea1757e254193630d0e4309cd3942ab6b26f787`。

先做 24 局执行冒烟；然后在 dev 偏移 21000，两个对手分布各对每个策略跑 128 局。
三个策略是原 v0.2、循环退出候选、原有七次移位限制。八席轮换，同种子、同规则、同打乱轮次调度。
七次限制只是预先指定的旧控制，不因这次分数较好临时改为最终候选。

在开发结果前保存 `PROTOCOL.json`：候选在两场景的名次均值退步不超过 0.15、移位减少至少 50%、
且无无效/未完成局时，进入独立复核。开发阶段通过后先保存 `HOLDOUT_FREEZE.json`，再运行
final 偏移 70000 的每场景每策略 256 局，只比较原 v0.2 与不再改动的候选。
未使用 v0.2 旧 final 偏移 50000 选模。这些新种子从此也不再是未来可重复选模的未见验收集。

主指标是平均名次（越低越好），同时保留吃鸡率、前四率、失败/中断/非法动作、延迟、移位和上限事件。
名次差置信区间以完整八席种子块 bootstrap；每个复核场景只有 32 个环境种子块，不能把 256 席当作独立种子。
相同初始种子在策略分叉后会改变卡池和后续随机调用路径，不保证后续商店相同。

结果表与结论见本页下方；逐局数据、源码覆盖包和配置指纹见 `runs/practice-followup-20261028/`。
首轮开发输出未汇总延迟分位数，逐局延迟及加权均值存在；复核已补齐全量决策延迟汇总。

## 运行

在仓库根目录，使用已安装的本地 `.venv`；每条命令的输出目录必须不存在：

```bash
.venv/bin/python -m omnibob.practice_review \
  --session runs/practice-20261028-103720 \
  --checkpoint runs/releases/omnibob-v0.2-20261028/policy/policy.pt \
  --output runs/my-practice-review/analysis.json

.venv/bin/python -m omnibob.experiment_reorder \
  --checkpoint runs/releases/omnibob-v0.2-20261028/policy/policy.pt \
  --variants baseline cycle_exit cap7 --opponents scripted \
  --split dev --seed 21000 --games 128 --workers 2 --max-seconds 900 \
  --output runs/my-reorder-scripted

.venv/bin/python -m omnibob.experiment_reorder \
  --checkpoint runs/releases/omnibob-v0.2-20261028/policy/policy.pt \
  --variants baseline cycle_exit --opponents heuristic \
  --split final --seed 70000 --games 256 --workers 2 --max-seconds 900 \
  --output runs/my-reorder-heldout-reproduction

.venv/bin/python -m pytest tests -q
```

后两条评测命令分别复跑已使用的开发和验收种子，不构成新的独立验证。
`--games` 是每策略局数，必须为 8 的倍数；最多两个 CPU worker、每个模型一个推理线程。
时间预算在原生调用之间检查，超时记录为中断并以非零状态退出，不把中断写成名次。
硬杀进程不能保证写出最终汇总；已写 `games.jsonl` 和 manifest 的计划局数用于发现缺失记录。
所有这些命令都不读取凭据、不访问网络、不排队。

这些输入必须使用与冻结权重相容的卡表、observe2、动作编码及引擎；加载器仍拒绝不匹配版本。
新候选的入口是 `load_reorder_policy` 和上述实验 CLI，不应伪装成被冻结包的默认部署配置。

## 实测结果与决策

开发集，平均名次：

| 对手 | 冻结 v0.2 | 循环退出 | 旧七次限制 |
| --- | ---: | ---: | ---: |
| 脚本 | 2.2812 | 2.3438 | 2.1953 |
| 启发式 | 2.7969 | 2.7500 | 2.4844 |

旧七次限制在这批开发种子上分数较好，但此前开发对照也出现过退步。本轮未将它临时选为新赢家，
不在反复观察后改写候选规则。开发结果不能替代独立验收。

独立复核，每行 256 局：

| 对手 / 策略 | 平均名次 | 吃鸡率 | 前四率 | 平均移位/局 | 触及额度/局数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 脚本 / v0.2 | 2.0742 | 37.9% | 96.1% | 230.61 | 143/256 |
| 脚本 / 循环退出 | 2.1367 | 38.3% | 93.0% | 26.24 | 2/256 |
| 启发式 / v0.2 | 2.6953 | 38.3% | 81.2% | 204.07 | 131/256 |
| 启发式 / 循环退出 | 2.5859 | 42.2% | 82.0% | 25.32 | 1/256 |

循环退出减去原版的配对名次差（负数有利）：

- 脚本：+0.0625，95% 区间 [-0.1329, +0.2695]。
- 启发式：-0.1094，95% 区间 [-0.3867, +0.1641]。

**结论：操作效率改善成立，强度改善未证实；不能声称已证明不退步。**
两场景合计平均移位减少 88.14%，触及上限的对局从 274/512 降至 3/512。
两个区间均跨 0，上界也未同时低于预设 +0.15；因此没有通过强度提升或非劣性的晋级标准。
冻结 v0.2 不替换，候选作为独立本地工具保留。没有新权重、线上成绩或排名结论。

候选首次偏离 practice 原动作发生在第 7 回合：它把回到旧站位的动作替换成卖随从。
这恰好说明动作屏蔽会影响经营选择，不能把原录像后面的动作直接拼到候选前缀上估计结果。

残余问题已用开发种子 1000021006、席位 5 重现：第 12 回合有 27 次取消，和移位交织，
最后剩 6 金币仍触及上限。此处是新的本地诊断，不是原 practice 的事实。
原始证据在 `runs/practice-followup-20261028/remaining-cap-diagnostic.json`。

复核期间 CPU 单次决策的加权均值：
- 脚本：v0.2 1.479 ms，候选 1.603 ms。
- 启发式：v0.2 1.528 ms，候选 1.653 ms。

循环触发时会多一次模型前向，单次调用不更快；收益来自大幅减少调用次数。
这是两个并行 worker 且部分时段有测试任务的运行延迟，不是隔离机器上的硬件极限。

验证记录：

- 正式本地对照 1,792/1,792 局完成，另 24/24 局冒烟完成；均无失败、中断、截断或非法动作。
- 超短时限故障探针刻意中断 8/8 局，退出码 1、完成数 0，全部留档并排除于强度统计。
- 105 项 Python 测试通过；新边界包括真实引擎移位、对手公开更新、相同卡不同身材、非移位后重新排列、
  只有移位时合法兜底、允许八次不重复移位，以及真实协议形状的终局日志白名单。
- 原发行包 1,924 文件、原 practice 23 文件全部通过原 SHA256 清单，原比赛压缩包哈希不变。
- 本轮未修改 Rust 引擎，因此未重新编译或将旧 Rust 测试结果冒充本轮新结果。

协议、结果、源码身份、复盘数据与测试输出保存在 [证据目录](evidence/omnibob-practice-followup/README.md)。

## 下一项最值得做的实验

仍保持冻结权重，单独比较“取消后即清空本段历史”与“跨移位保留同一施法的取消历史”。
目标是消除打出—取消—移位复合循环，同时保留新的有效目标和真正改变后的经营机会。
先用残余反例验证行为，再在新开发种子比较名次、金币未用完的上限事件和决策数；
选定后另留新验收种子。它仍是待验证假设，不能直接把所有 Cancel 禁掉，也不应自动上线。
本轮不继续叠加控制规则或扩大训练，以免用同一批已看过的结果选出一个看似更好的版本。
