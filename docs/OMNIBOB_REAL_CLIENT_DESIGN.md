# OmniBob 真实客户端纯模型操作设计

日期：2026-11-02；实现进展更新于2026-11-05。状态：已实现只读窗口采集与OCR入口，尚未实现自动对局。

## 目标与边界

冻结的OmniBob负责整局游戏决策，本地脚本负责可见画面采集和操作执行。用户只旁观、局外标注；紧急停止仍然可用。局内不更新权重，不用聊天模型替换OmniBob的动作选择。收集到的数据首先用于诊断，不自动进入PPO训练。

不能保证不被平台识别或封号。有人值守、科研用途和小号并不构成暴雪自动操作规则的例外。本设计不包含反作弊规避、伪装操作、进程注入或隐藏信息读取。允许自动操作的测试环境与官方匹配的规则边界必须区分，不将可运行等同于平台许可。

本次用户请求为设计，不构成开始真实比赛、解除历史STOP、变更默认发行或启动新训练的执行指令。

## 当前实际能力

- `omnibob/arena.py`连接的是结构化arena协议，不是炉石屏幕。
- `omnibob/observation_v2.py`要求4017个数值特征、447个卡牌索引和245个合法动作标志；合法性目前由模拟器提供。
- v0.4是通过本地确认的隔离候选，v0.3仍为默认，v0.2保留回退。
- 尚无真实客户端画面识别、特征转换、鼠标动作执行及动画后验证实现。
- 官方客户端当前版本、卡表、英雄/机制覆盖与模型语义兼容性未实测。不得因为维度相等就声明可用。

## 最小闭环

屏幕采集 → 可见状态重建 → 语义兼容性检查 → 冻结模型决策 → 单次UI操作 → 新画面核验 → 下一次决策。

### 1. 可见状态重建

固定游戏窗口、分辨率、缩放和语言，使用本机图像识别/OCR，避免依赖付费API。只记录当前玩家本来能够看到的屏幕信息及此前确实看到的信息；对手情报保留观察时间，不将旧阵容当当前阵容。

识别阶段、回合、时限、金币、生命、酒馆等级、商店、手牌、己方阵容、英雄技能、发现/选目标界面，以及可见卡牌属性与附加效果。悬停查看说明属于观测操作，不算策略动作，仍记录其耗时。

建立逐字段映射表：来源像素/历史可见事件、单位、置信度、刷新时机、是否可准确还原、是否与模型训练语义一致。不能恢复的字段列为缺口，不填成看似真实的零值。

如果模型依赖的关键特征无法从可见信息恢复，或当前机制超出模型支持范围，先完成输入适配或另行设计新观测版本；不得强行沿用旧权重并把结果称为同一个OmniBob。

### 2. 决策与合法动作

每次调用使用同一个冻结checkpoint及固定运行时（初期保留RepeatGuard1），显式指定候选路径，不改变发行默认值。视觉模块不替模型选牌、决定阵容或编造策略理由。

真实客户端没有现成的`legal_mask`。需要根据可见阶段、资源、对象、容量及已核实规则重建，并用实际UI状态校验。未知合法性必须显式报告。暂停/错误保护与模型动作分别记账，不把保护规则伪装成模型决策。

首版必须覆盖完整一局会遇到的选英雄、购买、出售、打出、指定目标、磁力、发现、刷新、冻结、升本、英雄技能、移动及结束回合。未支持的强制选择界面意味着本次运行不具备整局可用性，不能靠无限等待掩盖。

### 3. 操作执行

模型给出语义动作及对象标识后，执行器映射为点击或拖拽。一个游戏动作可以包含必要的按下/拖动/释放，但不能预排一串未经后续画面确认的经营动作。

执行前确认游戏窗口焦点、阶段与目标仍有效。执行后按动作预期检查金币、卡牌所在区域、阵容顺序或界面阶段的变化。效果未知时重新观察，禁止盲目重发购买/出售等可能重复生效的操作。

等待依据是动画结束和画面稳定，不以模仿真人或规避检测为目标。操作耗时、识别耗时和模型推理耗时分别记录。

### 4. 运行控制

- 独立于识别和推理循环的紧急停止，取消未执行动作并释放鼠标按键；恢复必须显式进行。
- 窗口失焦、用户移动/点击接管、未知卡牌/机制、低置信度关键状态、动作效果无法确认、断线等情况停止新操作并留档，不自动抢回控制。
- 整场固定模型、执行器、视觉配置和规则映射版本；禁止局中换模型或修参数。
- 运行前固定最多局数和绝对截止。首个端到端验证建议仅一局；以后可预先授权小批次，不使用无限排队。
- 回合时限不足时不得继续发起来不及确认的复杂动作；具体保留时长由离线实测确定并预先冻结。
- 故障退出和人工接管单列，不纳入“纯模型完整对局”成绩。自然结束、模型策略失败和执行器故障分别记录。

## 数据与复盘

每次决策保存：截图时间与文件、状态解析及置信度、模型输入、合法掩码、模型原始动作、实际执行动作、执行前后对象映射、确认结果、耗时、保护/接管事件、模型/源码/规则版本。优先裁剪游戏窗口，避开登录和账号信息。

局后保存名次、对局耗时、有效决策数、识别失败、执行失败、超时、经营停滞及移位占比。用户标注绑定原事件，原始记录不改写。标注可以表示错误类型、替代动作、理由及判断置信度。

首批对局只能提供真实环境诊断，不凭几局名次宣称强于v0.3。人工替代动作不是原策略采样，不能直接混入原PPO轨迹；未来训练必须独立处理干预和分布差异。

## 实现顺序与完成标准

1. **兼容性清点**：读取客户端实际可见版本与画面，完成卡表/机制和输入字段映射。交付明确支持范围与未解决缺口。
2. **离线闭环**：从真实录屏/截图重建状态，人工核对关键字段及合法动作；验证模型可稳定接收真实输入。只用预选容易画面不足以验收。
3. **执行器验证**：在允许的受控环境测试主要动作和失焦、重复执行、动画、强制选择、暂停边界；必须核验真实UI变化，mock不替代。
4. **有界整局**：在明确授权及确定的使用环境内，固定一局、固定checkpoint、用户旁观，完整留档，结束即停。仅全程无需人工补救且记录完整才称为端到端完成。

当前最先需要解决的是输入与客户端兼容性。不要先写连续点击脚本，再用无法确认的模型状态驱动真实操作。该路线用于验证与采集真实反馈；“更强对手能否改善训练”的因果问题仍由独立本地配对实验回答。
